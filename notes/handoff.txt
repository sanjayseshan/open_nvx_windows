## Win98 3D: transport groundwork, renderer not connected yet

```text
D3D9 app -> Wine9x D3D9 switcher (`nine`) -> Mesa Gallium Nine (`mesa99.dll`)
  -> Nouveau/NVC0 winsys -> Win98 client transport -> NVX.VXD
  -> shared miniport/OpenRM/GSP -> GA104
```

- Added `submodules/wine9x` at upstream revision `3fbe3fd` as a pinned reference. Its D3D9 switcher can route applications to `mesa99.dll`; it is a front-end router, not the GPU driver. Project-specific patches must live outside this submodule.
- Existing `src_driver/nvxmp.c` has the XP miniport 3D IOCTL set (client/session, BO allocation, upload/download, batch submit, wait fence, present).
- New uncommitted work adds a bounded DIOC allowlist for the shared 3D IOCTL ABI, serializes Win9x process-tag selection with `HwStartIO`, adds `mesa_patches/nvx_winsys_win9x.c` to map Mesa escape IDs to VxD IOCTLs, and stops advertising direct-map support in the Win98 build. `./src_win98/build.sh` succeeds and emits an updated `dist_win98/nvx.vxd`.
- This is transport groundwork only: the VxD package was not installed in the running guest, the new adapter is not yet linked into the Win98 Mesa ICD/Nine build, and no 3D app has exercised it.
- `src_win98/shim/nvx_mdl_win98.c:NvxMdlMapUser()` deliberately fails closed. The Win98 adapter can use upload/download paths, but map-dependent BO behavior and Nouveau screen creation still need to be checked end to end.
- Next: integrate the DIOC adapter into a reproducible Win98 `nvxogl32.dll`/Nine build outside the submodule, prove caps/client/BO upload and a GPU clear+readback, then triangle/depth, textures and present. Preserve miniport/OpenRM validation and packet construction. Keep user mapping disabled until a real safe VMM process mapping exists.
- Do not claim D3D hardware acceleration based on DirectDraw capability bits or a software HAL. Current evidence for Win98 is 2D solid fills only.

## Constraints and current test setup

- The 16-bit driver currently uses private development VxD PM ID `0x7d00`; replace it with a collision-free assigned ID before distribution.
- `DibEngine=0` is needed for this accelerated BitBlt route. DIBENG otherwise bypasses the driver's callback.
- Keep SYSTEM.INI mouse settings exactly `[boot] mouse.drv=mouse.drv` and `[386Enh] mouse=*vmouse`; cursor movement still needs visual confirmation.
- No secondary-monitor/QHD hardware test while the current single-head VM remains running.
