## .299: use OpenRM continuation records and independent queue pointers

Large OpenRM page-list registrations use one ordinary RPC element followed
by function-71 continuation elements. The prior XP code instead treated the
whole PFN list as one 16-element contiguous record. .299 ports the upstream
chunking pattern, waiting for command-ring slots as needed. It also consumes
replies through the status queue's own ReadPtr; command and status rings have
independent producer/consumer pointers, and continuation chunks make their
positions diverge. Startup event polling now follows the same status-ring
ownership. Host tests verify frame checksums, full multi-frame page-list
reconstruction, separate queue pointers, and successful allocation/free.
Hardware validation is pending. Files: src_driver/nvx_gsp.c,
src_driver/nvx_gsp_boot.c, src_driver/nvx_rpc.{c,h},
src_driver/tests/{rpc_test.c,gsp_mock_test.c}.

## .295: correct GA100-only MMU-lock policy; preserve native modesets

Root cause found: our FRTS layout applied `memmgrReadMmuLock_GA100`
semantics to GA104. OpenRM's generated `g_mem_mgr_nvoc.c` dispatches that
implementation ONLY on GA100; GA104 selects `memmgrReadMmuLock_e133c0`,
which returns valid=FALSE. Captured GA104 raw registers (LO=0x100000,
HI=0x1effff0) must therefore not clamp WPR below 256 MiB. That clamp placed
GSP firmware/heap below 256 MiB and left only ~60 MiB available. Earlier
statements below that the whole boot calculation matched upstream were
incorrect: they overlooked chip HAL dispatch. No reserved GSP region is
being overridden; the corrected boot layout must produce its own region table.

Changes:
- `NvxComputeFrtsLayout` now accepts the hardware chipset, decoded from
  PMC_BOOT_0. Only chipset 0x170 (GA100) interprets MMU lock registers.
  Captured GA104 0x174 register regression checks retain top-of-VRAM WPR.
- Separate coherent page-table backing maps up to 8 GiB of physical VRAM
  at GPU VA 4 GiB. Sixteen PD0 pages and 4096 large-page leaf tables avoid
  the low GART/upload VA ranges. Allocation still obeys GSP free bounds.
- Mesa GETPARAM_FB_SIZE no longer caps VRAM at 32 MiB; miniport caps expose
  the mapped firmware-approved region size. Both ICD builds need rebuilding.
- Once healthy native display channels own scanout, `NvxVbeSetMode` returns
  to the caller's native modeset path without INT10 or releasing channels.
  This avoids release -> BIOS failure 0x57 -> channel-recreation timeout,
  which caused both monitors to enter standby in .294.

Validation so far: VBE mock and GSP host tests pass, including directory/leaf
coverage and unchanged upload mapping. Hardware test pending. Check new FRTS
WPR end near 8 GiB, firmware free region, NV170 rendering, 3DMark allocations,
and native mode transitions. Do not claim 3DMark or standby resolved until
hardware evidence is available.

The 128 MiB figure is the GPU virtual mapping aperture. The 460 MiB GART is
system memory and currently supports linear BOs. Neither increases tiled local
VRAM. GSP reports the other framebuffer ranges with nonzero `reserved` values;
OpenRM's `memmgrInitGspClient()` marks those ranges reserved, and its allocator
does not use them. The MMU lock and WPR calculations in this boot follow the
same policy as upstream, so expanding the page table or ignoring those ranges
would risk overwriting firmware or VBIOS-protected memory. The `.293` log
therefore does not prove a parser or aperture-size bug.

The `.292` 3DMark run did not exit; its log shows repeated framebuffer heap
exhaustion, but no new `NV01_MEMORY_LOCAL_USER` unsupported status or MMU
fault. Firmware assertion count remains at the startup baseline of 1.

Next: investigate whether the current VBIOS MMU lock / GSP region table is
expected for this card and boot state. For immediate 3DMark progress, trace
the many persistent pre-benchmark BOs and close-session lifetime, then explore
only memory placements Nouveau supports. Upstream NVC0 uses GART for linear
BOs and requests VRAM for block-linear miptrees, so sending kind-6 tiled
surfaces through the present GART path is not a safe drop-in fix. Do not map
or allocate from the firmware-reserved ranges without proving an upstream
allocation path authorizes them.

## Submission-path optimization

`NvxWinsysSubmitBatch` previously allocated a temporary heap buffer and copied
every translated batch into it just to insert the staging pushbuffer BO
reference before the command dwords. It now inserts that reference in place in
the caller-owned translation buffer, using `memmove` for the overlapping
dword/relocation tail, and submits the expanded buffer directly. The API takes
the caller's capacity and rejects batches without room for the extra reference.
This removes one allocation/free and one full-batch copy per kick; it does not
change the NVX ABI or GPU ordering. This change was built and hardware tested in .257 and later.

The miniport still waits for each GPU fence before returning from
`NvxGspSubmitNvc0Batch`. Removing that wait could offer a larger gain, but needs
fence-based lifetime protection for every referenced BO and the staging ring;
do not remove it until that asynchronous ownership path is implemented.

Both XP x64 and x86 Mesa WGL ICDs built successfully with the in-place change
using `test/build_mesa_xp64.sh` and `test/build_mesa_xp32.sh`. The full .257
VFIO run is recorded above. No FPS improvement has been demonstrated.

## Changes that restored drawing

1. Nouveau maps BOs shared read/write upstream; its access flags describe
   synchronization. It legitimately calls BO_MAP(access=0) and writes data.
   XP patches 0012/0028 labelled these mappings READ, while the old submission
   loop skipped their uploads. The old whole-BO upload also risked replacing
   GPU-written neighbours with stale CPU data.
2. v236 introduced baseline-based changed-dword publication for every mapped
   BO referenced by a submission, independent of map access labels. Initial
   publication initializes undefined GPU backing to match the shadow, including
   zero stores. Refresh merges pending CPU changes, and partial uploads retain
   stale read-freshness until a real download. Final failed unmaps retain data.
   Existing vertex-range helpers now publish pending changes without replacing
   unchanged words. Host regressions cover these ownership/freshness cases.
3. v236 hardware could not exercise drawing: VRAM-to-GART TLS fallback reset
   requested 128 KiB alignment to 4 KiB. GPUVA 0x12a10000 then failed our own
   alignment check (kind=8/f=1, Error allocating TLS area), forcing GDI Generic.
   Log: test_logs/v3.0.0.236-20261116-181522.log.
4. v237 preserves the original TLS alignment across fallback. GEM regression
   deliberately starts at the observed misaligned hole; its mock now models
   64 KiB minimum alignment rather than hiding the problem with 2 MiB rounding.
   Hardware rendering and visually correct gears were then verified.

The coherency changes corrected the observed drawing. We did not isolate which
old input range or whole-BO overwrite produced the original missing red gear.

## Normal allocation / upstream comparison

The v235 allocation changes are retained and committed. XP build scripts no
longer apply forced-linear/shared-target patch 0023 or depth-kind-zero patch
0024. ABI 22 carries tile mode and an 8-bit memory kind in the existing fixed
allocation size. Miniport installs VRAM PTE kinds, invalidates once per range,
and restores kind zero before free; kinded sizes are rounded to 64 KiB.
GART remains linear and cannot silently replace tiled/kinded storage.

Observed kinds are consistent with pinned Nouveau TU102+ policy: generic
color uses kind 6, and the selected S8Z24 depth uses kind 3. Earlier notes
expecting color kind 0xfe were incorrect for Ampere. OpenRM/UVM establishes
PTE encoding and kernel ownership; Nouveau generates OpenGL draw/target state.
