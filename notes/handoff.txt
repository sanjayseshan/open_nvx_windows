## Win98 3D: transport bridge in progress

```text
D3D9 app -> Wine9x D3D9 switcher (`nine`) -> Mesa Gallium Nine (`mesa99.dll`)
  -> Nouveau/NVC0 winsys -> Win98 client transport -> NVX.VXD
  -> shared miniport/OpenRM/GSP -> GA104
```

- Added `submodules/wine9x` at upstream revision `3fbe3fd` as a pinned reference. Its D3D9 switcher can route applications to `mesa99.dll`; it is a front-end router, not the GPU driver. Project-specific patches must live outside this submodule.
- Existing `src_driver/nvxmp.c` has the XP miniport 3D IOCTL set (client/session, BO allocation, upload/download, batch submit, wait fence, present).
- Commit `23b4d1e` adds a bounded DIOC allowlist for the shared 3D IOCTL ABI, serializes Win9x process-tag selection with `HwStartIO`, maps Mesa escape IDs to VxD IOCTLs in `mesa_patches/nvx_winsys_win9x.c`, and suppresses unsupported direct-map capability in the Win98 build. The Win98 VxD package builds successfully.
- Current changes route Mesa WGL bridge requests through `NvxWinsysEscape`, include the Win9x adapter in the external Mesa source patch, and let `NVX_WIN98_DIOC` select the DIOC backend. Both the normal x86 Mesa 25.1.6 XP ICD and the full x86 Nouveau/WGL DIOC smoke build compile and link. The DIOC artifact is isolated under `/tmp/nvx-mesa-win98-dioc-build`; it was built with Mesa's XP API floor, so it is not yet a Win98-installable ICD. Its imports are `GDI32`, `KERNEL32`, `MSVCRT`, and `USER32`; Win98 export and subsystem compatibility are still unverified.
- The VxD package was not installed in the running guest, and no Win98 3D app has exercised the transport or rendered on GPU. Do not report Win98 3D acceleration as working yet.
- `src_win98/shim/nvx_mdl_win98.c:NvxMdlMapUser()` deliberately fails closed. The Win98 adapter can use upload/download paths, but map-dependent BO behavior and Nouveau screen creation still need to be checked end to end.
- Next: produce an actual Win98 API-floor ICD (or identify and shim every unavailable Mesa import), audit imports/subsystem against Win98 exports, then install the VxD/ICD in a separate guest snapshot. Prove caps/client/BO upload and GPU clear+readback, then triangle/depth, textures and present. Preserve miniport/OpenRM validation and packet construction. Keep user mapping disabled until a real safe VMM process mapping exists.
- Do not claim D3D hardware acceleration based on DirectDraw capability bits or a software HAL. Current evidence for Win98 is 2D solid fills only.

## Constraints and current test setup

- The 16-bit driver currently uses private development VxD PM ID `0x7d00`; replace it with a collision-free assigned ID before distribution.
- `DibEngine=0` is needed for this accelerated BitBlt route. DIBENG otherwise bypasses the driver's callback.
- Keep SYSTEM.INI mouse settings exactly `[boot] mouse.drv=mouse.drv` and `[386Enh] mouse=*vmouse`; cursor movement still needs visual confirmation.
- No secondary-monitor/QHD hardware test while the current single-head VM remains running.
