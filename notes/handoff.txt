## Likely performance constraint and next steps

The tested 3DMark path is x86 WineD3D over the WGL ICD. Wine is pinned to 1.7.55; `wine/dlls/wined3d/cs.c` installs only `wined3d_cs_st_ops`. The guest batch writes `csmt=1`, but this source has no worker-thread command-stream implementation, so that setting does not provide CSMT. This serial D3D9-to-OpenGL path is a strong CPU-side bottleneck candidate; game 2 at 4 FPS may also be limited by shader/GPU work. Measure a clean benchmark before assigning percentages.

1. Fix 3DMark automation path detection and log `dir`/`if exist` results inside the guest. Confirm the exact running EXE and retain the per-game FPS / score output.
2. Fix the first Shader Program Header 18 fault from .345 by tracing NVC0 shader BO upload, VA, contents, and lifetime. Do not accept a score from a run with this fault.
3. Profile one clean 3DMark run: per-game frame times, host CPU utilization, NVC0 submissions, and fence waits. Compare against the user's 2600 / 17-4-18 baseline.
4. Evaluate an XP-compatible WineD3D command-stream worker or a supported newer WineD3D. Backporting CSMT is a substantial separate change; registry configuration alone is insufficient in this Wine source.
5. Gallium Nine remains separate and unproven: earlier runs had incorrect/black rendering and failed pixel proof. Recent 3DMark runs use WineD3D.
