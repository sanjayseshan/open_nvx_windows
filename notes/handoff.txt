Log: `test_logs/v3.0.0.242-20261116-203141.log`. The freshly built XP x64
Mesa Nouveau ICD took the GPU-to-scanout route. 64-bit gears reported 23.667

The x86 Mesa ICD was not rebuilt. The system has
`i686-w64-mingw32-gcc-posix` but lacks `i686-w64-mingw32-g++-posix`, which
Meson needs for the x86 build. The recorded 18 FPS x86 gears run used the
previous packaged DLL and does not validate this change.

For the same 300x300 source image, the miniport logged scanout destinations
`0x20039810` and `0x22039810`, 32 MiB apart. Both active heads received copies.
This appears consistent with the XP dual-view/clone setup; check intended
monitor topology before restricting copies to one head. Current copies wait
for the Mesa staging blit fence and synchronously submit CE copies per visible
rectangle.

Performance is still limited by synchronous work: the cube submitted 1,201
GPU batches in 300 frames (about four per frame), and each NVC0 batch polls for
its fence before returning. The new present route also waits for the staged
blit and CE copy. Logging may add overhead because `LogStr` serializes
characters through polled COM1, but batch, upload, wait, and present IOCTL
messages are suppressed and the log has no per-frame batch trace. The current
run cannot isolate the logging cost; compare a diagnostics-light run and add
timings around submit, stage blit/fence, and CE copy.

## Changes that restored drawing

1. Nouveau maps BOs shared read/write upstream; its access flags describe
   synchronization. It legitimately calls BO_MAP(access=0) and writes data.
   XP patches 0012/0028 labelled these mappings READ, while the old submission
   loop skipped their uploads. The old whole-BO upload also risked replacing
   GPU-written neighbours with stale CPU data.
2. v236 introduced baseline-based changed-dword publication for every mapped
   BO referenced by a submission, independent of map access labels. Initial
   publication initializes undefined GPU backing to match the shadow, including
   zero stores. Refresh merges pending CPU changes, and partial uploads retain
   stale read-freshness until a real download. Final failed unmaps retain data.
   Existing vertex-range helpers now publish pending changes without replacing
   unchanged words. Host regressions cover these ownership/freshness cases.
3. v236 hardware could not exercise drawing: VRAM-to-GART TLS fallback reset
   requested 128 KiB alignment to 4 KiB. GPUVA 0x12a10000 then failed our own
   alignment check (kind=8/f=1, Error allocating TLS area), forcing GDI Generic.
   Log: test_logs/v3.0.0.236-20261116-181522.log.
4. v237 preserves the original TLS alignment across fallback. GEM regression
   deliberately starts at the observed misaligned hole; its mock now models
   64 KiB minimum alignment rather than hiding the problem with 2 MiB rounding.
   Hardware rendering and visually correct gears were then verified.

The coherency changes corrected the observed drawing. We did not isolate which
old input range or whole-BO overwrite produced the original missing red gear.

## Normal allocation / upstream comparison

The v235 allocation changes are retained and committed. XP build scripts no
longer apply forced-linear/shared-target patch 0023 or depth-kind-zero patch
0024. ABI 22 carries tile mode and an 8-bit memory kind in the existing fixed
allocation size. Miniport installs VRAM PTE kinds, invalidates once per range,
and restores kind zero before free; kinded sizes are rounded to 64 KiB.
GART remains linear and cannot silently replace tiled/kinded storage.

Observed kinds are consistent with pinned Nouveau TU102+ policy: generic
color uses kind 6, and the selected S8Z24 depth uses kind 3. Earlier notes
expecting color kind 0xfe were incorrect for Ampere. OpenRM/UVM establishes
PTE encoding and kernel ownership; Nouveau generates OpenGL draw/target state.

## Remaining issues and next work

1. **Performance and presentation:** correctness is improved, but the CPU
   presentation path is expensive. The x64 GPU-to-scanout route is now
   verified. NvxGspSubmitNvc0Batch waits for each batch fence before
   returning, polling in 100 us intervals and serializing CPU/GPU work. WGL
   blits to a reusable linear GART stage, waits for its fence, then
   synchronously submits CE copies per visible rectangle; unsupported layouts
   retain the CPU/StretchDIBits fallback. VRAM raw
   downloads use a 4 KiB scratch window and a separate completed CE copy for
   each chunk (360000 bytes at 300x300 means 88 chunks if read via this helper).
   GART-backed staging downloads have a direct CPU-copy path and avoid that
   VRAM scratch loop; do not assume every present incurs those 88 CE copies.
   Shadow scans, changed-word uploads, waits, and serial diagnostics add cost.
   GPU timing/clock measurements have not been collected, so no percentage
   attribution or GPU power-state diagnosis is established. 3.0.0.242 reports
   59.9 FPS for the cube and 23.667 FPS for x64 gears with probes enabled.
   `LogStr` sends characters through polled COM1, but high-frequency batch,
   upload, wait, and present IOCTLs are suppressed; compare a diagnostics-light
   run before assigning most slowdown to logging. Next time submit, stage
   blit/fence, and CE copies, then consider batching or async work while
   retaining coherency correctness. The fresh x86 build is blocked by the
   missing i686 MinGW C++ compiler. Captures and first-48 range sample
   readbacks themselves add diagnostic overhead; current FPS is not a clean
   production benchmark. Fine-grained changed runs may issue many small uploads.
2. **Direct3D / 3DMark05:** x86 WGL hardware rendering is verified, but the
   user's 3DMark05 run reported near-zero FPS and then black screens. Verify
   its 32-bit D3D9-to-WineD3D-to-WGL renderer and repair the mode-set and large
   allocation failures above. The existing 64-bit D3D9 smoke test crashes with
   0xC0000005; a successful WGL gears run does not establish D3D9 works.
3. **WineD3D identity / crash:** D3D9 loads and creates IDirect3D9, identifies its adapter as GTX
   470/nv4_disp.dll, then the 64-bit test crashes (0xC0000005). Trace the failing
   D3D caps/device call and collect a crash address/stack. The adapter name is
   consistent with WineD3D's capability-based fallback identity, not a change
   in physical GPU. Upstream select_card_handler/wined3d_guess_card uses a
   fallback when renderer matching fails; its NVIDIA D3D11 fallback is GTX470.
   The NT5 driver-name table supplies nv4_disp.dll. The packaged old DLL has
   these strings/functions; its exact build revision and decision trace have
   not been established. Reference source:
   https://github.com/wine-mirror/wine/blob/wine-3.0/dlls/wined3d/directx.c
   Expose actual PCI identity through an appropriate query or adapt WineD3D's
   renderer mapping later; changing the label alone does not improve rendering.
4. **Test reporting:** batch ERRORLEVEL is expanded inside parenthesized blocks,
   so recorded child return codes can be stale. The final PASS is unconditional.
   Correct those and report per-application failures, including x86 availability.
5. **Capacity:** only the confirmed aperture-backed VRAM heap is allocated;
   the 64.5 MiB TLS BO falls back to GART. Preserve placement and alignment.
   Broader VRAM management and shader-TLS placement remain performance work.
6. **Firmware / synchronization:** investigate the initialization assertion.
   XP patch 0020 still bypasses the upstream WGL end-of-frame wait, while the
   CPU texture transfer supplies its own synchronization. Audit this lifecycle
   before expanding asynchronous/multiple-application workloads.
