## WineD3D assessment

The `wine` submodule is pinned at `a786dca9` (`wine-1.7.55`). The current Wine 11.x line includes years of D3D/WineD3D fixes and is worth an isolated XP-targeted A/B build for compatibility and CPU overhead. This log has no explicit WineD3D shader compile error before the hardware fault. It reports the GL path and a card-detection warning: vendor `0000`, fallback to renderer `NV170`. That may affect Wine’s feature selection, but does not by itself explain the GPU Shader Program Header exception. A newer WineD3D may improve behavior/performance; it is not yet a demonstrated fix for the RC fault. Preserve Wine as a submodule and keep local changes in `wine_patches/`; audit XP imports and APIs before installation. The new WineD3D Vulkan renderer is not used by this OpenGL path.

Official references: [Wine 11.x release notes](https://www.winehq.org/news/11) and [Wine 9.10 announcement](https://www.winehq.org/news/79).

## Current performance change

`mesa_patches/nvx_xf86drm.c` now caches 32 recent GPU-address-to-BO resolutions. The XP libdrm shim previously scanned all 2,048 BO slots for each raw NVC0 GPU address; repeated shader/texture/vertex addresses now use cache hits validated against the live slot, BufferId, VA, and size. A cache miss retains the full scan and ownership checks. x64/x86 Mesa ICD builds pass and import only `GDI32.dll`, `KERNEL32.dll`, `msvcrt.dll`, and `USER32.dll`. FPS impact is unmeasured; compare a hardware run against .319 before calling it an improvement.

Other measurable differences from Linux Nouveau/OpenRM:

- CPU shadow BO writes can cross an XP escape and invoke a synchronous CE upload for each changed span. Linux has native shared/GART mappings and orders M2MF uploads in the graphics push stream. Profile frequency/time before changing synchronization.
- The XP shim copies/parses/validates each batch, resolves GPU-address references in user mode, and serializes callers. Linux uses native DRM GEM handles/relocations and kernel pushbuf validation.
- Fence/BO retirement uses a bounded 32-batch pending table and ring-slot waits. Measure actual queue depth and wait time before changing limits.
